# 气量智能问数：Text-to-SQL 的落地实践

> 让业务人员用自然语言直接查数据，是 AI 落地的典型场景。这篇文章复盘我做的"气量智能问数"系统的完整设计。

## 背景与痛点

气量系统的数据分析需求高度动态：客户今天想看"各营业厅上月用气量"，明天想看"某片区异常表具"。传统做法是**每个统计维度都定制开发一张报表**，需求一变就要改代码，多个项目重复定制，成本极高。

我们的目标：**让业务人员用一句话，就能得到想要的查询结果**。

## 核心难点：自然语言 → SQL 的鸿沟

Text-to-SQL 难在几个地方：

1. **表结构复杂**：几十张业务表，字段多、关系复杂，LLM 不可能全部记住
2. **业务术语**："用气量"在库里可能叫 `gas_consumption`，"营业厅"叫 `business_hall`
3. **SQL 不可控**：LLM 直接生成的 SQL 可能语法错、逻辑错，甚至越权查数据

## 架构设计

整体链路：

```text
用户提问
   ↓
① 意图理解 + 实体抽取（LLM）
   ↓
② 动态关联表结构（工具：查 schema + 表关系）
   ↓
③ SQL 生成（LLM + 注入相关表结构）
   ↓
④ SQL 校验与执行（工具：语法校验 + 权限校验 + 执行）
   ↓
⑤ 错误反馈与重试（执行失败 → 带回错误重生成）
   ↓
⑥ 结果转自然语言（LLM）
```

### 动态 Schema 注入

关键设计是**不让 LLM 背全部表结构，而是按需注入**。先让 LLM 判断问题涉及哪些表，再用工具把这几张表的 schema、字段注释、表间关系**动态喂给 LLM**：

```python
# 工具：根据问题返回相关表结构
def get_relevant_schema(intent, entities):
    tables = infer_tables(intent, entities)  # 判断涉及哪些表
    return build_schema_prompt(tables)        # 拼接表结构 + 字段注释
```

### 术语映射

把业务术语和库表字段的映射（"用气量"→`gas_consumption`、同义词等）也作为上下文提供给 LLM，显著提升 SQL 准确率。

### SQL 安全三件套

Text-to-SQL 最怕的是"查错数据"和"越权"：

1. **语法校验**：执行前先做 SQL 语法检查
2. **权限控制**：自动注入数据权限过滤（如当前用户能看的租户/片区范围）
3. **错误重试**：SQL 执行报错时，把错误信息带回 LLM 重新生成，最多重试 N 次

## 落地效果

系统上线后，原本"每个维度定制一张报表"的模式，变成了"一句话即查"。多个项目复用了同一套智能问数能力，重复定制成本大幅降低。

## 小结

Text-to-SQL 看起来是"让 LLM 写 SQL"，真正的功夫在**工程**：动态 Schema 注入、术语映射、SQL 校验与权限控制。这些才是让 AI 从"能回答"到"能安全可靠地回答"的关键。
