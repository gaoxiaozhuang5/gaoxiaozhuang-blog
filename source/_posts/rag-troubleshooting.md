# RAG 检索效果差，应该怎么排查

> RAG 效果差的表象是"答得不对"，但根因可能在数据、切片、检索、重排、生成任何一个环节。这篇文章给一套系统化的排查路径。

## 先定位：是"检索不到"还是"生成错了"

RAG 的错误分两类，排查方向完全不同：

- **检索不到**：正确的文档没被召回 → 问题在检索链路
- **检索到了但答错**：文档对了，LLM 没用对 → 问题在 Prompt 或生成

一个简单的定位方法：**把检索到的内容打印出来看**。如果检索结果里根本没有答案，那就是检索问题；如果答案就在检索结果里却答错，那就是生成问题。

## 检索问题的排查清单

### 1. 数据质量

垃圾进，垃圾出。先检查文档本身：

- 文档是否完整、是否有乱码
- 是否有大量图片/表格没有解析出来
- 术语是否统一（"气量"和"用气量"是同一个东西吗）

### 2. 切片策略

切片直接决定检索粒度：

- 切片太短 → 语义不完整，召回碎片
- 切片太长 → 噪声多，稀释了关键信息
- 切片切断了语义 → 关键信息被拆到两个 chunk

### 3. Embedding 匹配度

用户问题和文档的表述方式往往不同。比如用户问"怎么提高燃气表的读数准确率"，文档写的是"表具计量误差"。语义向量可能匹配不上。

解法：**Query 改写**——先把用户口语化的问题改写成更接近文档风格，再做检索。

### 4. 检索方式单一

纯向量检索对专有名词、编号（如"设备编号 GB-001"）效果差。要引入**混合检索**：向量检索 + BM25 关键词检索，取长补短。

## 生成问题的排查

如果检索没问题，就看 Prompt：

- 检索结果是否**去重、排序**后喂给 LLM
- 是否明确要求"基于给定材料回答，材料没有就不答"
- 是否要求"引用来源"，防止幻觉

## 小结

RAG 优化是一个系统问题，不是"换个更好的 Embedding"或"换个更大的模型"能解决的。**先把检索内容打出来看**，定位是检索问题还是生成问题，再对症下药。这套排查思路，比任何单个技巧都值钱。
