# Embedding、Rerank 与向量数据库怎么配合

> 很多人把 Embedding、Rerank、向量数据库混为一谈。其实它们是检索链路上三个职责完全不同的角色，搞清楚边界，RAG 才搭得对。

## 三个角色的职责

| 角色 | 职责 | 类比 |
|------|------|------|
| Embedding | 把文本变成向量 | 给文字"翻译"成机器能算的坐标 |
| 向量数据库 | 存向量 + 快速找最近邻 | 一个能秒查"谁离你最近"的索引 |
| Rerank | 对初步结果精排 | 海选后的"复试官" |

## Embedding：语义的"翻译官"

Embedding 模型把一段文本映射成高维向量，语义相近的文本向量也相近：

```python
vec1 = embed("燃气表读数不准")
vec2 = embed("表具计量误差")
# vec1 和 vec2 的余弦相似度应该很高
```

选 Embedding 模型的要点：**领域适配**。通用模型在通用文本上够用，但如果你做的是燃气、巡检这类垂直领域，往往需要针对性的模型或微调。

## 向量数据库：海选的"索引"

向量数据库的核心是**近似最近邻（ANN）检索**，在海量向量里快速找出最接近的 K 个。

常见选型：

- **Milvus**：功能全、适合大规模
- **Qdrant**：轻量、Rust 实现、部署简单
- **pgvector**：PostgreSQL 扩展，适合已有 PG 的团队

对中小规模团队，`pgvector` 往往是最务实的选择——不用多维护一套数据库，SQL 和向量查询能一起用。

## Rerank：海选后的"复试"

Embedding 是**双向独立编码**，速度快但精度有损；Rerank 模型（Cross-Encoder）把问题和文档**拼在一起联合编码**，精度高但慢。

所以正确姿势是**两级检索**：

```text
向量检索（粗筛）→ 召回 Top 100
        ↓
Rerank（精排）→ 留下 Top 5
        ↓
喂给 LLM
```

第一级用 Embedding + 向量库，追求"快"和"全"；第二级用 Rerank，追求"准"。两者配合，才能兼顾召回率和准确率。

## 小结

RAG 的检索链路是**分工协作**：Embedding 负责翻译，向量库负责海选，Rerank 负责复试。理解三者的边界，你就知道什么时候该换 Embedding 模型、什么时候该上 Rerank，而不是盲目堆技术。
